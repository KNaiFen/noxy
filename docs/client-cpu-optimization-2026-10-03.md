# 客户端 CPU 优化记录

基准版本：`6906400`。Forge 1.20.1，Java 21，Windows。

## 算法降耗

同一线程执行旧版和新版 `RegionDiscovery`，直接读取线程 CPU 时间；不启动 Minecraft，也不使用异步调度。每种场景预热 10 次，再执行 300 次，共 3,600 次范围变化和 230,400 次请求。半径 192、硬限 256，距离档位 `32:0, 64:1, 96:2`，半径 128 内已有精细缓存。每次范围变化取出 64 个请求。

| 场景 | 旧版 CPU / ms | 新版 CPU / ms | 降幅 |
| --- | ---: | ---: | ---: |
| 单轴移动 | 34,312.500 | 812.500 | 97.63% |
| 斜向移动 | 37,187.500 | 1,187.500 | 96.81% |
| 连续转向 | 39,546.875 | 1,453.125 | 96.33% |
| 单轴移动并更新响应覆盖 | 36,843.750 | 890.625 | 97.58% |

每种场景的请求数量、剩余需求数量和请求顺序校验值均与旧版一致。单轴边界逐列检查由 203,366,400 次减至 11,491,200 次，目录列检查由 90,650,400 次减至 18,100,500 次。

保留的实现：

- 对范围和精度统一的方格批量设置掩码，只在边界细分；未变化区域继续复用。
- 只更新精度或包含关系改变的列，响应满足需求时保留请求队列。
- 利用凸形范围每行的连续最小值，每个区域只维护最多 32 个行首候选；按需推进行内候选。
- 缓存区域距离下界，目录查询复用区域顺序，取得最近请求后提前结束远区比较。
- 简化矩形最小值求解，删除分段边界搜索和临时形状分配；二次幂坐标分组改用位运算。
- 覆盖预算先尝试完整半径，只在预算不足时缩小；不重复构造页集合。

消融时移除了无收益的逐行浮点累加打分、行首打分缓存、旧排序游标和未使用的测试摄像机高度参数。

复现：先将基准版本解压到 `build/client-cpu-baseline`，在该目录构建 `compileJava processResources`，使用项目绝对路径的 `-PvoxyJar`；当前项目执行 `compileJava`。在已有 `build/benchmarks/lod-square256-cache128/client-launch.json` 的环境运行：

```bash
python tools/region-cpu-check.py --runs 300
```

输出保存到 `build/region-cpu-comparison.json`。本结果覆盖范围发现、掩码更新和请求选择，不能解释为整个 MOD、Minecraft 进程或 Voxy 渲染 CPU 降低 95%。解码、体素写入和网格计算不在该短基准内。

## 异步处理

接收会话的范围、目录、请求、网络拼片、解码应用、响应完成、重试、确认和索引 checkpoint 由单个低优先级后台线程顺序执行。主线程发布不可变输入，合并过期 tick；主线程入队不等待队列容量。原版区块和光照由主线程复制不可变快照，每 tick 调度预算 0.5 ms；单次快照复制可能超出预算。原版更新的版本钩子保留与原版网络包的顺序，只发布和合并更新意图。

移动采样由后台线程处理，队列保留最新输入并按实际 tick 间隔计算速度。快照带世界身份，重连或切换世界时不使用旧世界预测。本地生成的客户端交接使用原子引用，取消客户端 tick 与集成服务端生成之间的共享监视器。

Voxy 初始化、原版世界读取和不可变快照复制仍需要主线程；后台不会直接遍历实体或读取活区块。正常 tick 和关闭接收不等待后台覆盖索引锁，Voxy 整体关闭仍需等待资源清理。

## 已取得的 2,000 实体基准

一轮固定场景，每项 20 秒；猪具有正常 AI、重力、碰撞，放在高度 119 的地面，测量期间存活数最低均为 2,000，平均约 1,939～1,966 只发生移动。关闭 VSync，客户端帧率上限 260。先开启接收并等待 LOD 网格等队列稳定，再在同一会话切换接收和预测；横移路径为 x=-20、+20、0，z=1，速度 4.3 方块/秒，两端位置核验一致。

| 横移模式 | 旧版 1% low | 改版 1% low | 旧版 0.1% low | 改版 0.1% low | 旧版 >50 ms 帧数 | 改版 >50 ms 帧数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 接收关闭 | 25.2 | 33.4 | 12.7 | 30.1 | 2 | 0 |
| 接收开启 | 23.9 | 36.4 | 15.0 | 34.1 | 2 | 0 |
| 接收和预测开启 | 17.4 | 34.9 | 9.8 | 30.5 | 7 | 0 |

low 定义为最慢 1% / 0.1% 帧的平均耗时取倒数。此轮每项约 1,300 帧，0.1% low 只包含约 2 帧，因此仅作卡顿基准，不作稳定置信区间。两版的接收关闭结果也有差异，不能把全部 FPS 差值归因于 MOD。原始记录：`build/client-cpu-check-1791002289854191100/results.json`。

此轮使用异步加第一阶段算法优化，随后继续完成行候选排序等优化。按用户要求不再增加实体压力测试轮次；最终算法收益使用前述同工作量短基准验证。

## 正确性验证

- `gradlew test smokeClasses build` 通过。
- 12 个方向的 512 次请求逐个与穷举全排序比较；2,000 个随机矩形与数值凸搜索比较。
- 独立比较旧版几何：200,000 个矩形，分类相同，最小值最大误差 `5.82e-11`。
- 独立比较旧版覆盖预算：500 个场景，包含未保存页，半径决策一致。
- 实际客户端请求完成检查通过：单列、批量、未变化响应、旧版本、晚到响应、原版卸载、脏列重试、请求公平性和会话切换。
- 后台持有覆盖索引锁时，主线程 tick、状态读取、区块钩子和关闭通过 50 ms 上限检查。
- 单人生成完成移动、停止、暂停、禁用与资源回收检查。
- 最终版联机重连、22 方块/秒转向和停止检查通过，接收 19,694 列 / 46.6 MiB，结束时请求和缓冲归零。
- 该功能检查的 JFR 中，MOD 执行采样有 1,021 次在接收线程，2 次在渲染主线程（tick 和入队）；未采到 MOD 在渲染主线程等待监视器。这是采样证据，不能作为任何情况下零阻塞的保证。
